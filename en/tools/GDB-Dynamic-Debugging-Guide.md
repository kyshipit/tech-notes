# Part Two: A Complete Guide to GDB Dynamic Debugging—From Coredump Analysis to Active Debugging

> **Applicable scenarios:**
>
> - The program crashed during runtime, and the cause of the crash needs to be located.
> - The program is behaving abnormally, and its execution flow needs to be traced.
> - I want to observe the memory state and variable changes during program execution.
>
> **What problems can this article help you solve?**
>
> - How do I get a coredump and analyze it when the program crashes?
> - How to deduce the root cause from the scene of the collapse?
> - How to actively debug a program that is running or about to run?
>
> **The difference between dynamic debugging and static analysis:**
>
> - Dynamic debugging: Observe the execution process while the program is actually running.
> - Static analysis: Analyzing binary files directly without running the program.
> - The two complement each other: dynamic debugging solves "where the crash occurred," while static analysis solves "what is the program's logic?"

## Chapter 1 Coredump Basics and Configuration

### 1.1 What is coredump?

A coredump file is a memory dump file generated by the operating system when a program crashes. It contains the memory state, register values, stack information, etc. at the time of the crash and is an important tool for debugging the cause of program crashes.

### 1.2 Conditions for coredump generation

**Necessary conditions:**

- A serious error has occurred in the program (such as segmentation fault, bus fault, etc.).
- The system coredump function is enabled.
- There is enough disk space
- Target directory with write permissions

**Common triggering situations:**

- Accessing a null pointer or wild pointer
- Memory out-of-bounds access
- Stack overflow
- Division by zero error
- Actively calling the abort() function

### 1.3 Troubleshooting methods for failure to generate coredump

#### 1.3.1 Check coredump size limit

```
ulimit -c
```

If it displays 0, it means it is disabled and needs to be set to unlimited.

View all restrictions:

```
ulimit -a
```

Temporary settings (valid for the current session):

```
ulimit -c unlimited
```

#### 1.3.2 Check file system permissions

Check target directory permissions:

```
ls -ld /tmp
```

Ensure the program has write permissions.

#### 1.3.3 Check process resource limits

View process limitations:

```
cat /proc/<pid>/limits
```

#### 1.3.4 Check if the program has processed the signal.

Some programs may capture crash signals and handle them automatically:

```
// 示例：程序捕获了SIGSEGV信号
signal(SIGSEGV, custom_handler);
```

#### 1.3.6 Using strace to trace system calls

```
strace -f -o strace.log ./your_program
```

#### 1.3.7 Check the apport or abrt service.

Ubuntu/Debian:

```
sudo service apport status
```

CentOS/RHEL:

```
sudo service abrt status
```

### 1.4 Explanation of WSL Special Mechanisms

In a traditional Linux environment, when an application crashes, the system might generate a core file containing a memory image of the application at the time of the crash. The kernel parameter `kernel.core_pattern` determines how these core files are generated. WSL's design has its own unique features:

Design Features | illustrate
:-- | :--
core_pattern points to the pipe | WSL by default sets kernel.core_pattern to a pipe command, meaning core data is not written directly to disk files but is instead handled by a specific program (such as `/wsl-capture-crash` ).
Core file generation is disabled by default. | By setting `ulimit -c 0` , WSL disables the generation of traditional core files within containers by default.

**The advantages of this design:**

- Enhance system security: Prevent core files from unintentionally recording sensitive information (such as passwords, keys, etc.) and storing it on the disk.
- Optimize the development experience: Pipe crash information to specific handlers for formatting, analysis, or integration with Windows-side debugging tools.

**Security Warning:** `/proc/sys/kernel/core_pattern` is a sensitive file that requires close monitoring. If it can be written to arbitrarily, especially in a container environment, it could be exploited to achieve container escape or privilege escalation.

**WSL's core dump mechanism:**

```
内核检测到段错误 → 准备生成核心转储
        ↓
检查 core_pattern → 发现要发送给 /wsl-capture-crash
        ↓
显示消息 → 内核固定显示 "Segmentation fault (core dumped)"
        ↓
实际处理 → WSL 的 CaptureCrash 服务接收并处理崩溃信息
        ↓
文件系统层面 → 没有生成传统的 core 文件
```

**Why does it display "core dumped"?**

- The kernel's message text is hard-coded; it neither knows nor cares about the actual dump target.
- From the kernel's perspective, it did indeed "dump" the kernel information—only through a pipe rather than a file.
- WSL has chosen to retain this traditional message, even though the actual mechanism is different.

**Traditional Linux vs WSL behavior comparison:**

Behavior | Traditional Linux | WSL
:-- | :-- | :--
Core dump target | document | Pipeline → Specialized Services
Limited by ulimit -c | yes | Unaffected by traditional document limitations
Generate core file? | generate | No generation

Therefore, in WSL, `Segmentation fault (core dumped)` should be understood as "a segmentation fault has occurred and the crash information has been captured", rather than "a core dump file has been generated".

### 1.5 Enable coredump generation

In this WSL configuration, generating a traditional core dump file requires modifying the core dump configuration.

#### Method 1: Temporarily effective (restores default settings after restarting WSL or the system)

```
echo "core-%e-%t-%p" | sudo tee /proc/sys/kernel/core_pattern
```

The changes have been successfully confirmed.

```
cat /proc/sys/kernel/core_pattern
```

#### Method 2: Permanent modification (This method is ineffective for WSL reboots and is applicable to traditional Linux distributions).

Edit the sysctl configuration:

```
sudo vim /etc/sysctl.conf
```

Add the following line:

```
kernel.core_pattern=core-%e-%t-%p
kernel.core_uses_pid=1
```

Apply configuration immediately:

```
sudo sysctl -p
```

#### Method 3: Restore WSL defaults

```
echo "|/wsl-capture-crash %t %E %p %s" | sudo tee /proc/sys/kernel/core_pattern
```

**Format instructions:**

placeholder | meaning
:-- | :--
%p | Process ID (PID)
%t | Dump time (UNIX timestamp)
%e | Executable filename

**Complete operation process example:**

```
# 1. 检查当前限制
ulimit -c
# 输出: 0

# 2. 检查core_pattern
cat /proc/sys/kernel/core_pattern
# 输出: |/wsl-capture-crash %t %E %p %s

# 3. 启用coredump
echo "core-p%p-t%t-%e" | sudo tee /proc/sys/kernel/core_pattern
ulimit -c unlimited

# 4. 确认设置
ulimit -c
# 输出: unlimited

# 5. 编译并运行程序
gcc -g -o bubble bubble.c
./bubble

# 6. 查看生成的core文件
ls -la core-*
# 输出: core-p12345-t1623456789-bubble

# 7. 用GDB分析
gdb ./bubble core-<pid>
(gdb) bt
```

## Chapter 2: Analyzing coredump files using GDB

### 2.1 Loading the coredump file

```
gdb <程序路径> <coredump文件路径>
```

Example:

```
gdb /usr/bin/myapp /tmp/core-myapp-12345-1623456789
```

### 2.2 Viewing the crash location and call stack

```
(gdb) bt          # 显示调用栈（backtrace简写）
(gdb) where       # 同bt
(gdb) bt full     # 显示调用栈和局部变量
```

### 2.3 Check Register Status

```
(gdb) info registers    # 显示所有寄存器
(gdb) info registers    # 简写: i r
```

Pay special attention to `rip` (the instruction pointer register in x86-64), which points to the execution address at the time of the crash.

### 2.4 View memory mapping

```
(gdb) info proc mappings
```

Output example:

```
0x555555554000     0x555555555000     0x1000        0x0 /home/musk/work/deliberate/algorithm/insertion
0x555555555000     0x555555556000     0x1000     0x1000 /home/musk/work/deliberate/algorithm/insertion
0x555555556000     0x555555557000     0x1000     0x2000 /home/musk/work/deliberate/algorithm/insertion
...
0x7ffff7dc9000     0x7ffff7deb000    0x22000        0x0 /usr/lib/x86_64-linux-gnu/libc-2.31.so
0x7ffff7fcf000     0x7ffff7fd0000     0x1000        0x0 /usr/lib/x86_64-linux-gnu/ld-2.31.so
```

**Normal address mode:**

- Program code segment: `0x55555555xxxx`
- Library code segment: `0x7ffff7xxxxxx` or `0x7ffffxxxxxxx`
- Stack: `0x7ffffffxxxxx`

### 2.5 Viewing Variables

```
(gdb) print variable_name      # 打印变量值
(gdb) p variable_name          # print的简写
(gdb) print *pointer           # 打印指针指向的值
(gdb) print array[5]           # 打印数组元素
(gdb) print $rax               # 打印寄存器值
```

View all local variables in the current stack frame:

```
(gdb) info locals
```

To view the parameters of the current function:

```
(gdb) info args
```

### 2.6 Check Memory

```
x`命令格式：`x/<重复次数><格式><大小> <地址>
```

**Format instructions:**

Format | meaning
:-- | :--
x | hexadecimal
d | Decimal
t | binary
c | character
s | String
i | Assembly instructions

**Size description:**

size | meaning
:-- | :--
b | byte (1 byte)
h | Half a character (2 bytes)
w | 4 bytes
g | Large characters (8 bytes)

**Common examples:**

```
(gdb) x/10wx &variable          # 以十六进制查看10个字
(gdb) x/20cb buffer             # 查看20个字节（字符形式）
(gdb) x/s str                   # 查看字符串
(gdb) x/g $rsp                  # 查看栈指针指向的内容
(gdb) x/10i $pc                 # 查看当前指令附近10条指令
(gdb) x/20xg $rsp               # 查看栈内容（20个巨字）
(gdb) x/10wx 0x7fffffffe110     # 查看指定地址的10个字
```

### 2.7 Stack Frame Operations

```
(gdb) backtrace           # 显示调用栈，简写: bt
(gdb) backtrace full      # 显示调用栈和局部变量
(gdb) frame <编号>        # 切换到指定栈帧，简写: f
(gdb) up                  # 向上移动栈帧（调用者方向）
(gdb) down                # 向下移动栈帧（被调用者方向）
(gdb) info frame          # 显示当前帧信息，简写: i f
(gdb) info locals         # 查看当前栈帧的局部变量，简写: i lo
(gdb) info args           # 查看当前函数的参数，简写: i ar
```

### 2.8 Thread Information

```
(gdb) info threads            # 显示所有线程，简写: i th
(gdb) thread <线程ID>         # 切换到指定线程
(gdb) thread apply all bt     # 查看所有线程堆栈
```

### 2.9 Disassembly

```
(gdb) disassemble         # 反汇编当前函数
(gdb) disas main          # 反汇编指定函数
```

### 2.10 Signal Information

```
(gdb) info signals        # 显示信号信息，简写: i sig
```

### 2.11 Example of an automation script

Create the debug script `debug_core.sh` :

```
#!/bin/
# debug_core.sh

if [ $# -ne 2 ]; then
    echo "用法: $0 <程序路径> <coredump路径>"
    exit 1
fi

PROGRAM=$1
COREFILE=$2

gdb -q $PROGRAM $COREFILE << EOF
set pagination off
bt
info registers
thread apply all bt
quit
EOF
```

How to use:

```
chmod +x debug_core.sh
./debug_core.sh ./bubble core-12345
```

## Chapter 3 GDB Troubleshooting Approach and Practical Application

> **The core idea** is to locate the problem from macroscopic symptoms to microscopic code errors, and to narrow down the scope of the problem by observing memory status and program behavior.

### 3.1 Troubleshooting Steps (Complete Case Demonstration)

Using the `insertion.c` program as an example, this demonstrates every step from crash to root cause location.

**Compilation preparation (with AddressSanitizer):**

```
gcc -g -fsanitize=address -fno-omit-frame-pointer -o insertion insertion.c
```

#### Step 1: Identify the problem phenomenon

```
(gdb) r
Program received signal SIGSEGV, Segmentation fault
```

**Observation:** Program crashes, segmentation fault **inference:** memory access violation (accessing memory it shouldn't have accessed).

**Checklist:**

- Mapping check: Is the address within the segment listed in `info proc mappings` ?
- Pattern check: Does the address conform to the system memory layout pattern?
- Symbol check: Can GDB resolve the function name?
- Numerical check: Does the address contain suspicious data patterns?
- Consistency check: Whether it is consistent with other register/stack values.

#### Step 2: Check the location of the crash

```
(gdb) bt
#0  0x00000003555550db in ?? ()
(gdb) info registers
rip            0x3555550db         0x3555550db
```

**Observation:** Call stack exception, RIP points to strange address `0x3555550db` **Inference:** The return address is corrupted, indicating that the stack memory was modified unexpectedly.

#### Step 3: Analyze memory mapping

```
(gdb) info proc mappings
0x555555554000     0x555555555000     0x1000        0x0 /home/musk/work/deliberate/algorithm/insertion
```

**Observation:** The normal code segment is in the range of `0x55555555xxxx` , but RIP points to `0x3555550db`

```
正常程序地址:   0x55555555558a  (在映射范围内)
异常的 rip:     0x00000003555550db (不在任何映射范围内)
                ^^^^^^^^^^
                异常的高位部分
```

**Inference:** The control flow is disrupted, most likely due to a stack overflow or buffer overflow.

#### Step 4: Check the stack and local variable state.

```
(gdb) info locals
arr = {10277, -402295808, -1772, -2125934455, 41156}
n = 32767
```

**Key finding: Local variable values ​​were corrupted.**

- `arr` is not the original `{98, 11, 45, 3, 65}`
- `n` is not the expected `5` , but `32767`

**Inference:** The stack memory was accidentally written to, corrupting local variables.

#### Step 5: Locate the crash code

```
(gdb) info frame
rip = 0x55555555558a in main (insertion.c:30)
(gdb) list
30      {
```

**Observation:** The crash occurs at the beginning of the main function (line 30). **Inference:** The problem occurs during the function call, not in the current line.

#### Step 6: Use memory testing tools to pinpoint the exact location.

```
gcc -g -fsanitize=address -o insertion insertion.c
(gdb) r
```

**Strategy:** Use AddressSanitizer to automatically detect memory errors **. Result:** Accurately located the stack buffer underflow in `insertion.c:19` (accessing `arr[-1]` ).

### 3.2 Explanation of the function of each parameter

parameter | effect
:-- | :--
`-g` | Includes debugging information, making bug reports clearer.
`-fsanitize=address` | Enable AddressSanitizer instrumentation to automatically detect memory errors.
`-fno-omit-frame-pointer` | Preserving frame pointers facilitates debugging and stack backtracking.

### 3.3 Problem Reasoning Chain

```
段错误
    ↓
内存访问违规
    ↓
异常rip地址 → 控制流/返回地址被破坏
    ↓
局部变量值异常 → 栈内存被意外修改
    ↓
崩溃在main开始 → 问题发生在之前的函数调用
    ↓
AddressSanitizer报告 → 精确定位到数组越界访问
```

### 3.4 Key Investigation Techniques

#### a. Observe memory state patterns

Phenomenon | infer
:-- | :--
Local variables are corrupted | Stack corruption
Return address error | Control flow hijacked
These two phenomena occur simultaneously | Buffer overflow

#### b. Use tools to assist

- GDB basic commands: `bt` , `info` , `x` are used for initial location.
- Memory detection tools: AddressSanitizer, Valgrind for precise location
- Observation point: `watch` for changes in key variables.

#### c. Combining algorithmic knowledge

- Knowing it's an "insertion" procedure → I speculate it's insertion sort.
- Common insertion sort errors → Cycle boundary issues, index out of bounds
- Stack buffer underflow → accessed `arr[-1]`

### 3.5 Summary of Experience

1. **Deducing the cause from the phenomenon** : There is a definite memory access error behind the anomaly.
2. **Delving deeper** : From crash symptoms → memory state → code location → specific error
3. **Combination of tools** : GDB for initial positioning + professional tools for precise positioning
4. **Integrating domain knowledge** : Algorithm characteristics help predict error types

This systematic troubleshooting method can be applied to debugging various memory-related problems. The key is to establish a reasoning chain from the phenomenon to the cause and to make good use of tools to verify each inference.

### 3.6 Valgrind Supplementary Notes

```
# 内存检查（追踪未初始化值的来源）
valgrind --tool=memcheck --track-origins=yes ./insertion

# 内存泄漏检查（完整报告）
valgrind --leak-check=full ./insertion
```

> **Note** : This chapter explains how to actively debug a program. It covers setting breakpoints, single-stepping, observing variable changes, and tracing the execution flow.

### 4.1 Compilation Preparation

#### 4.1.1 Debugging and Compilation Options

The `-g` option must be added during compilation to preserve debugging information:

```
gcc -g -o program program.c
```

```
CFLAGS = -g -Wall
```

```
file program

```

```

```

```

### 4.3 Program Execution Control

```

```

### 4.4 Breakpoint Management

#### 4.4.1 Setting breakpoints

```
(gdb) break main              # 在main函数设置断点，简写: b
(gdb) break 15                # 在第15行设置断点
(gdb) break file.c:20         # 在指定文件的第20行设置断点
(gdb) break function          # 在指定函数设置断点
(gdb) break *0x400512         # 在内存地址设置断点
(gdb) tbreak main             # 设置临时断点（触发后自动删除），简写: tb
```

#### 4.4.2 Conditional Breakpoints

```
(gdb) break func if i>5      # i>5时断点触发
(gdb) break file.c:20 if i == 5
(gdb) condition 2 i > 10     # 为断点2设置条件
(gdb) ignore 2 5             # 忽略断点2的前5次触发
```

#### 4.4.3 Breakpoint Management

```
(gdb) info breakpoints       # 查看所有断点，简写: i b

#### 4.4.4 List of Breakpoint Commands

### 4.16 Actual debugging example (bubble.c)

#### Example program code

```
#include <stdio.h>
#define ARRAY_COUNT(arr) (sizeof(arr) / sizeof(arr[0]))

int arr[] = {9, 23, 86, 12, 34};

int main(int argc, char const *argv[])
{
    int temp = 0;
    for (int i = 0; i < ARRAY_COUNT(arr)-1; i++)
    {
        for (int j = 0; i < ARRAY_COUNT(arr)-i-1; j++)
        {
            if (arr[j] > arr[j+1])
            {
                temp = arr[j];
                arr[j] = arr[j+1];
                arr[j+1] = temp;
            }
        }
    }
    for (int i = 0; i < ARRAY_COUNT(arr); i++)
    {
        printf("arr[%d] = %d\n", i, arr[i]);
    }
    return 0;
}
```
