# AI engineering implementation related

# Part 1: Overall Cognitive Framework of AI

## 1.1 End-to-End Serial Logic

**Core workflow: Model (brain) → Quantization/Distillation/Pruning (lightweight adaptation) → Agent (autonomous decision-making hands and feet) → Skill (domain toolkit) → RTK/DCP (token cost optimization)**

**Complete implementation process** :

1. **Base acquisition** : Train or open-source to acquire general-purpose large models (LLaMA, GPT, Claude, etc.) with basic reasoning and knowledge capabilities.

2. **Lightweight Model** : By employing three key techniques—quantization, distillation, and pruning—the model size is compressed, computational power consumption is reduced, and the model is adapted for deployment on cloud/edge devices.

3. **Agent engineering** : Encapsulate lightweight models into intelligent agents (OpenCode, Cursor, Claude Code), giving them the ability to autonomously plan, decompose tasks, and invoke tools.

4. **Domain-specific capability empowerment** : Configure standardized skill sets for agents and implement them in vertical scenarios (code review, UX design, engineering development, etc.).

5. **Efficiency and cost optimization** : Token consumption is optimized through tools such as RTK and DCP, and context redundancy is reduced, which significantly reduces inference costs and improves response speed.

## 1.2 The essence of the LLM+Agent combination

### Key conclusions

The effectiveness of AI tools depends on both **the capabilities of the model's foundation** and **the implementation of the Agent project** ; neither can be neglected. All Agent capabilities, intelligent interactions, and tool calls are essentially **context-text-driven token probability predictions** , without any additional black-box logic.

### Unified underlying capabilities: Everything is context

All advanced AI capabilities will ultimately be transformed into text, inserted into the LLM context window, and used by the "predict the next token" model for unified reasoning.

- **CoT (CoT)** : A "self-thinking draft" generated by the model within a context to assist in step-by-step reasoning.

- **Tool Use/MCP** : The context is pre-stored with tool descriptions and input parameter specifications, the model outputs the calling instructions, and the tool execution results are appended back to the context, forming a closed loop.

- **Agent Loop** : A continuous iterative process of "thinking - calling tools - obtaining results - appending context".

- **Skills package** : Domain operation manuals and scenario specification texts, loaded into the context as needed.

- **RAG retrieval enhancement** : Fragmented text retrieved from external knowledge bases is pieced together into the context to aid reasoning.

- **Memory system** : Accumulates valid information across sessions and automatically loads it into the context when a new session starts, achieving "long-term memory".

### The core value of gradual disclosure

The model's native capabilities are fixed; **the quality, quantity, and organization of contextual information** directly determine the agent's upper limit. From Function Calling to MCP to Skills to progressive disclosure, the core goal of all technological iterations remains the same: **to efficiently organize information within a limited context window, avoid token explosion and information overload, and maximize the release of the model's inference capabilities** .

## 1.3 Context and Token Underlying Mechanism

### 1.3.1 Context Definition

The context is essentially **a messages array** . All inputs sent to the LLM are collectively called Prompts, and the messages array is the only carrier of Prompts.

### 1.3.2 Basic Token Rules

A token is the smallest unit of text processed by LLM: a common English word is about 1 token, and a single Chinese character is about 1-2 tokens. The number of tokens directly determines the inference time, billing cost, and context usage.

Request content | Number of messages | prompt_tokens
--- | --- | ---
Send only "Hello" | 1 item | 5
Send only "What is my name?" | 1 item | 7
Ask the question "What is my name?" while carrying the complete conversation history. | 5 items | 63

The core principle is that the longer the dialogue history, the larger the messages array, the higher the prompt_tokens, the higher the cost and latency.

### 1.3.3 Stateless Core Characteristics of the Model

LLM API calls **are completely stateless** , each request is independent, and the model does not automatically retain any session memory.

The essence of multi-turn dialogue is **to manually carry the complete history of dialogue messages** with each API request. All AI dialogue and AI programming tools on the market are based on this logic at the underlying level, with only the upper layer encapsulating optimization strategies such as context compression, redundancy filtering, and history pruning.

# Part Two: Principles of Quantization

## 2.1 Deep Learning

### 2.1.1 Tensors

Tensors are the sole data carrier in deep learning; essentially, they are multidimensional arrays. Model inputs, network weights, intermediate features, and inference outputs are all tensors. They include 0-dimensional single values, 1-dimensional vectors, 2-dimensional matrices, and 3/4-dimensional batch feature maps.

**Output tensor** : The feature data output after each layer of the network has performed operations. It is the core object of quantization calibration, accuracy verification, and tensor statistics.

**Tensor distribution** : the statistical regularity of tensor values ​​(mean, variance, extreme values, distribution pattern). The core objective of quantization is **to preserve the consistency of tensor distribution before and after quantization to the greatest extent possible** and avoid precision distortion.

### 2.1.2 Cosine Similarity

The value ranges from [-1, 1] and measures the overlap between tensors and feature vectors: the closer to 1, the higher the consistency of features before and after quantization and the fewer lost points; the lower the value, the more severe the feature distortion and the worse the inference accuracy. It is the core verification indicator for RKNN embedded quantization deployment.

### 2.1.3 Difference between floating-point and fixed-point numbers

- **Floating-point FP** : The decimal point floats, with a large range and high precision; commonly used are FP32, FP16, and BF16; PyTorch/ONNX models default to FP32 full precision.

- **Fixed-point type** : The decimal point is fixed, the hardware only stores integers, and the decimal is mapped by scale; commonly used are INT8 and INT4; a special format for edge NPU quantization inference.

## 2.2 Differences between mainstream network architectures

### 2.2.1 CNN Convolutional Neural Network

Focusing on visual tasks (YOLO, ResNet, MobileNet), the core four-layer structure is as follows:

- **Convolutional layer (Conv** ): Extracts image features layer by layer (shallow texture, medium shape, deep contour).

- **Batch Normalization (BN)** : Regularizes tensor distribution, prevents numerical explosion/disappearance, and improves quantization stability.

- **Activation layer** : Introduces non-linearity to allow the model to learn complex visual features.

- **Pooling layer** : Reduces dimensionality and computational power, preserves core features, and compresses feature map size.

### 2.2.2 Differences between CNN and Transformer

Comparison Dimensions | CNN | Transformer
--- | --- | ---
Feel the wild | Partial sliding windows require stacking multiple layers to expand the field of view. | Global receptive field, single layer covers the entire map
Weight sharing | Supported, small number of parameters | Not supported, large number of parameters
Computing power consumption | Low | high
Tensor Distribution | Stablize | Large fluctuations
Quantitative friendliness | Excellent, compatible with edge NPUs | Poor quality, prone to accuracy loss, requires high calibration standards.

ViT/Transformer has no convolutional or pooling layers; its core consists of multi-head self-attention, layer normalization, and a feedforward network.

## 2.3 Model Quantization

### 2.3.1 The Essence of Quantification

Converting FP32 floating-point tensors to INT8/INT4 fixed-point integers for inference storage achieves the following: reduced model size, memory saving, improved NPU inference speed, and compatibility with edge hardware.

### 2.3.2 Quantization Granularity

- **Coarse-grained per-Tensor** : The entire tensor uses the same scale/zero point, which is fast but has poor accuracy.

- **Fine-grained Per-Channel** : Single-channel independent statistical maximum and minimum values, independent quantization parameters, small error and high accuracy, making it the standard configuration for RKNN industrial deployment.

### 2.3.3 Core Quantization Parameters

- **scale factor** : the scale for converting between floating-point and fixed-point numbers, where integer + 1 corresponds to the floating-point increment; the larger the scale, the coarser the quantization precision.

- **zero_point** : The integer position corresponding to floating-point 0, used to shift the numerical range, adapt to unsigned integers to store negative numbers, uniquely calculated by the tensor's maximum and minimum values, and cannot be manually tampered with.

### 2.3.4 RKNN Quantization Calibration Logic

FP32 lossless inference must be performed using a real calibration set to obtain the minimum/maximum values ​​(min/max) of tensors for each layer and channel before valid scale and zero point can be calculated; calibration without real data will cause quantization parameters to fail and model accuracy to collapse.

## 2.4 Tensor Memory Layout Format

- **NCHW (default for training framework)** : Batch-Channel-Height-Width, native PyTorch/ONNX format, stored as a whole image per channel.

- **NHWC (Hardware Native)** : Batch-Height-Width-Channel, native hardware support for RKNN/NPU/Android, continuous pixel storage, higher memory read efficiency and faster inference.

Adaptation solution: RKNN-Toolkit2 automatically completes the NCHW→NHWC conversion without requiring manual code modification.

## 2.5 RKNN Core Memory Objects

- **rknn_context context handle** : global manager for the model and NPU, storing model address, hardware status, tensor memory, and inference configuration. All APIs depend on this handle.

- **The rknn_tensor_attr tensor attribute structure** stores the tensor shape, data type, quantization parameters, and memory format, and is used to guide preprocessing, dequantization, and buffer allocation.

Tensor memory is divided into: attribute configuration memory and actual data buffer memory.

## 2.6 RKNN Runtime C API Standard Lifecycle (Irreversible)

The project has a fixed calling process, and all embedded RK deployments follow this uniformly:

1. **rknn_init** : Loads the model, initializes the NPU, creates the context, and requests hardware resources.

2. **rknn_query (first time)** : Queries basic model information, input/output shape, and quantity.

3. **rknn_query (second time)** : Queries detailed tensor attributes, quantization parameters, and memory format.

4. **rknn_inputs_set** : Binds preprocessed NHWC format input data.

5. **rknn_run** : Distributes inference tasks, and the NPU performs forward computation.

6. **rknn_outputs_get** : Reads NPU inference results for post-processing and dequantization.

7. **rknn_destroy** : Releases resources and destroys the context to prevent memory leaks.

# Part Three: Practical Application of AI Toolchains

## 3.1 Model Optimization

Optimization technology | Core Principles | Should the structure be changed? | Should we retrain? | Core benefits
--- | --- | --- | --- | ---
Quantification | FP32→INT8/INT4 precision compression | no | No need for (post-training quantization) | Volume reduced by 75%, speed increased by 3-5 times
Pruning | Remove redundant weights/neurons | yes | Optional fine-tuning | Significantly reduce the computational cost of FLOPs
distillation | Large model teaches small model, transfer ability | yes | Complete training required | The small model approximates the inference performance of the large model.

In the PyTorch→ONNX→RKNN deployment pipeline: quantization is **a mandatory core step** , while pruning and distillation are optional pre-optimization steps.

### Model working link

1. **Research and development training** : architecture design, large-scale pre-training (such as 70B LLaMA).

2. **Optimized compression** : distillation, pruning, quantization, fine-tuning, and lightweight model.

3. **Conversion and deployment** : ONNX format conversion, engine adaptation (RKNN/TensorRT), service-oriented/edge deployment.

## 3.2 Agent

## 3.5 ONNX Model Dimension Validation

### 3.5.1 Four-layer verification dimensions

1. **Structure layer (Netron visualization)** : Quickly compares network topology and operator distribution, suitable for qualitative inspection.

2. **Operator layer (Python script)** : Accurately extracts operator types, attributes, and sequences, and verifies the consistency of the model skeleton.

3. **Weighting layer (cosine similarity)** : quantizes weight bias and determines quantization/conversion accuracy loss.

4. **Logical layer (ONNX Runtime)** : Input unified data for comparison and output, verifying complete equivalence of functions.

### 3.5.2 Verification Code

```Plain
import onnx
from onnx import helper

def extract_ops_info(model_path):
    model = onnx.load(model_path)
    ops = []
    for node in model.graph.node:
        op_info = {
            'name': node.name,
            'op_type': node.op_type,
            'input': list(node.input),
            'output': list(node.output),
            'attributes': {}
        }
        for attr in node.attribute:
            op_info['attributes'][attr.name] = helper.get_attribute_value(attr)
        ops.append(op_info)
    return ops

# 调用示例
your_ops = extract_ops_info('your_model.onnx')
official_ops = extract_ops_info('official_model.onnx')
print(f"当前模型算子数: {len(your_ops)} | 官方模型算子数: {len(official_ops)}")
```

```Plain
import onnx
from onnx import numpy_helper
import numpy as np

def load_weights(model_path):
    model = onnx.load(model_path)
    weights = {}
    for initializer in model.graph.initializer:
        weights[initializer.name] = numpy_helper.to_array(initializer)
    return weights

your_weights = load_weights('your_model.onnx')
official_weights = load_weights('official_model.onnx')

for name in your_weights:
    if name in official_weights:
        w1 = your_weights[name].flatten()
        w2 = official_weights[name].flatten()
        cos_sim = np.dot(w1, w2) / (np.linalg.norm(w1) * np.linalg.norm(w2))
        if cos_sim < 0.9999:
            print(f"权重异常: {name} 余弦相似度={cos_sim:.6f}")
        else:
            print(f"权重正常: {name}")
```

```Plain
import onnxruntime as ort
import numpy as np

def compare_outputs(model_a_path, model_b_path):
    sess_a = ort.InferenceSession(model_a_path)
    sess_b = ort.InferenceSession(model_b_path)

    input_name = sess_a.get_inputs()[0].name
    input_shape = sess_a.get_inputs()[0].shape
    input_shape = [d if isinstance(d, int) else 1 for d in input_shape]
    dummy_input = np.random.randn(*input_shape).astype(np.float32)

    out_a = sess_a.run(None, {input_name: dummy_input})
    out_b = sess_b.run(None, {input_name: dummy_input})

    for idx, (oa, ob) in enumerate(zip(out_a, out_b)):
        if np.allclose(oa, ob, rtol=1e-4, atol=1e-6):
            print(f"输出{idx}: 完全匹配")
        else:
            print(f"输出{idx}: 误差超标，最大偏差={np.max(np.abs(oa-ob))}")

compare_outputs('your_model.onnx', 'official_model.onnx')
```

### 3.5.3 Verification Conclusion

Operator + attribute consistency = model skeleton consistency; high weight similarity = lossless accuracy; output perfect match = **complete functional equivalence, can be directly replaced and deployed** .

## 4.4 Ultralytics Device Alignment Error Solution

Problem: Manually creating a CPU tensor does not match the GPU model device, triggering a type error.

Solution: Execute `tensor.to(device)` on the input tensor to align it to the device; or directly use the high-level `model()` interface (automatic preprocessing + device alignment).
