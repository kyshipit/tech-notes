## 一、ROS2 基础概念

### 1.1 ROS2 是什么

ROS（Robot Operating System）诞生于2007年，它并非传统意义上的操作系统，而是一个**分布式机器人软件开发框架**。其核心价值在于通过标准化的通信中间件，实现传感器、控制器、决策模块的**解耦开发**——你可以单独开发激光雷达驱动、运动控制算法和导航逻辑，最后像搭积木一样把它们拼起来。

ROS2 于2018年发布，是 ROS1 的完全重构。**ROS1 Noetic 已于2025年5月停止维护**，而 ROS2 Jazzy Jalisco 是当前活跃的长期支持版本（LTS），官方支持将持续到2029年。ROS2 的核心改进在于通信架构——从依赖中央节点的 TCP 通信，升级为去中心化的 **DDS（Data Distribution Service）** 通信机制。

**DDS 是什么？** 简单理解：ROS1 的通信像“打电话需要先拨总机”，所有节点必须先连接到 ROS Master 才能找到彼此；ROS2 的 DDS 像“微信群聊”——每个节点加入同一个“域”（Domain），就能自动发现其他节点并直接通信，没有单点故障。这种去中心化架构让 ROS2 可以运行在从嵌入式设备到云端服务器的各类平台上。

### 1.2 四大通信原语

ROS2 中节点（Node）之间通过四种方式交换信息：

| 通信方式              | 特点                              | 类比         | 典型应用                 |
| :-------------------- | :-------------------------------- | :----------- | :----------------------- |
| **Topic（话题）**     | 异步发布-订阅，一对多，持续数据流 | 广播电台     | 激光雷达点云、摄像头图像 |
| **Service（服务）**   | 同步请求-响应，一对一             | 打电话问路   | 地图查询、路径规划请求   |
| **Action（动作）**    | 可反馈、可取消的长任务            | 外卖订单追踪 | 导航任务、机械臂运动     |
| **Parameter（参数）** | 节点配置与运行时动态调整          | 系统设置     | PID参数、传感器配置      |

### 1.3 TF2 坐标变换

TF2 是机器人运动控制的“数学骨架”——没有它，激光雷达测到的距离、里程计算出的位移、摄像头看到的物体位置，全部无法统一到同一个空间坐标系下。

**为什么需要 TF2？** 机器人身上的传感器分布在不同位置：激光雷达在车顶、IMU 在底盘中心、摄像头在车头。激光雷达测得“障碍物在左前方 2 米”——这是相对于激光雷达自身的坐标。但控制机器人避障需要知道“障碍物相对于机器人中心（base_link）在什么位置”。TF2 做的事情就是：**维护一个从全局地图到每个传感器坐标系的变换树**，让任何节点都可以随时查询任意两个坐标系之间的变换关系。

典型的 TF2 树结构：

text

```
map → odom → base_footprint → base_link → laser_link
                                       → camera_link
                                       → imu_link
```



- `robot_state_publisher`：解析 URDF，发布所有静态坐标变换（如 base_link 到 laser_link 的相对位置）
- 里程计节点：发布动态变换 `odom → base_footprint`（机器人每走一步，这个变换都在变）
- 定位节点：发布 `map → odom`（将机器人位置对齐到全局地图）

## 二、机器人建模与观测

### 2.1 从 CAD 到 URDF——建模不是“写代码”

你可能以为机器人建模就是在文本编辑器里写 URDF 的 XML 代码。但**实际工程中，图形化建模才是主流起点**。

**真实工作流：CAD 画图 → 导出 URDF → 微调优化 → RViz 可视化验证**

**（1）CAD 画图（工程级工具）**

机器人结构设计首先在专业 CAD 软件中完成。主流工具：

- **Onshape**：云端 CAD 平台，**2026年3月起已原生支持 URDF 导出**，无需外部转换工具。2026年5月的更新进一步扩展了 URDF 导出功能，支持 frames、tool center points、更清晰的关节定义和更一致的命名规则，网格导出支持 STL 和 GLTF 的可调节细分质量。
- **SolidWorks**：最主流的桌面机械设计软件。官方提供 `sw_urdf_exporter` 插件，但需注意该插件**默认导出 ROS1 格式**，需手动修改配置文件适配 ROS2 Jazzy。社区也出现了 **SW2GZ** 等新工具，支持将 SolidWorks 装配体直接导出到 ROS2 + Gazebo（无需手写 URDF），已实现在 ROS2 Jazzy + Gazebo Harmonic 上的端到端测试。
- **Fusion 360**：同样有社区维护的导出工具。

**（2）导出 URDF**

CAD 插件会自动识别装配体中的零件和约束关系，生成：

- 每个零件 → 一个 `<link>`（刚体）
- 装配约束 → `<joint>`（关节）
- 自动计算质量、惯性矩、碰撞体

**（3）微调优化（导出后必做清单）**

CAD 导出的 URDF 通常不能直接用于仿真，必须手动调整：

| 调整项          | 原因                                               | 具体操作                                                  |
| :-------------- | :------------------------------------------------- | :-------------------------------------------------------- |
| **惯性参数**    | CAD 导出的惯性矩基于理想均匀密度，实际重心可能偏移 | 根据实物或详细设计修正 mass 和 inertia 矩阵               |
| **关节限位**    | CAD 装配约束不一定反映真实关节运动范围             | 检查并设置 `<limit>` 标签的 lower/upper                   |
| **传感器挂载**  | CAD 中可能未画激光雷达/IMU                         | 手动添加 `<gazebo>` 标签和传感器定义                      |
| **碰撞体简化**  | CAD 导出的碰撞体往往过于精细（原始网格）           | 简化为 box/cylinder/sphere 等基本几何体，提高物理引擎效率 |
| **ROS2 兼容性** | SolidWorks 官方插件默认导出 ROS1 格式              | 修改 URDF 中的标签和属性适配 ROS2                         |

**（4）RViz 可视化验证**

用 RViz2 加载 URDF，3D 查看模型结构、关节运动是否正常。

### 2.2 URDF 的核心结构与关键陷阱

URDF 的核心是 **link（刚体）+ joint（关节）** 构成运动学链：

xml

```
<robot name="mbot">
  <link name="base_link">
    <inertial> ... </inertial>    <!-- 质量 + 惯性矩阵 -->
    <visual> ... </visual>       <!-- 显示几何 -->
    <collision> ... </collision> <!-- 物理碰撞体 -->
  </link>

  <joint name="left_wheel_joint" type="continuous">
    <parent link="base_link"/>
    <child link="left_wheel_link"/>
    <origin xyz="0.2 0.1 0.04" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
  </joint>
</robot>
```



**陷阱一：根 link 不能带惯性**

`robot_state_publisher` 底层使用 **KDL（Kinematics and Dynamics Library）** 解析运动学链。KDL 要求根 link 必须是**无惯性、无几何的纯坐标 frame**。如果根 link 带 `<inertial>`，KDL 解析整个链条失败——**所有 TF 都不发布**，RViz 报 `Frame [base_link] does not exist`。

正确做法：用 `base_footprint`（空 link）作根，`base_link`（带惯性）作其子。这恰好符合 Nav2 的惯例：`odom → base_footprint → base_link`。

**陷阱二：`<cylinder>` 的朝向**

URDF 中 `<cylinder>` 的 `length` 沿局部 **Z 轴**——不是 X 轴，不是 Y 轴。要让圆柱体轮子“立起来”（盘面朝前后方向），需绕 X 轴旋转 90°：`rpy="${pi/2} 0 0"`。绕 Y 轴或 Z 轴旋转都会导致轮子“平躺”或“侧歪”。

### 2.3 可视化观测层——开发者的“眼睛”

可视化工具不是独立功能，而是**贯穿全流程的调试观测层**。在动手做任何仿真或控制之前，先掌握“怎么看”比“怎么做”更重要。

**（1）RViz2——3D 可视化**

ROS2 标配的 3D 可视化工具。可以显示：

- URDF 机器人模型（3D 渲染）
- 激光雷达点云
- TF 坐标轴
- 路径、代价地图、导航目标点

适用场景：**查看“空间对不对”** ——模型是否完整、传感器数据是否在正确位置。

**（2）PlotJuggler——时间序列分析**

专门分析数值数据随时间变化的工具。支持拖拽加载 rosbag2、MCAP 或实时 Topic 数据，用硬件加速 OpenGL 渲染大规模数据集。可以用公式创建新通道、做数据滤波。

适用场景：**查看“数值对不对”** ——PID 响应曲线、速度指令跟踪情况、传感器噪声分析。

**（3）Foxglove Studio——全栈可视化**

基于浏览器的现代可视化平台，原生支持 MCAP 格式。可同时显示 3D 模型、2D 地图、图像、时间序列曲线等多种面板。支持实时远程连接和遥操作。

适用场景：**全系统联调**——同时看模型、地图、图像、信号，快速定位跨模块问题。

## 三、仿真验证

### 3.1 Gazebo 的工作原理

Gazebo 是 ROS 生态系统的**官方标配仿真器**，由 Open Robotics 基金会维护。当前主流版本是 **Gazebo Harmonic（gz-sim8）** ，与 ROS2 Jazzy 是官方推荐组合。例如，开源项目 `rbot` 已实现将机器人描述、Gazebo 仿真、`ros2_control`、遥操作、传感器仿真、定位、建图和 Nav2 导航整合到一个 ROS2 工作空间中。

**物理引擎在做什么？**

物理引擎的本质是求解刚体动力学方程——**给定所有关节受到的力，计算机器人每个部件下一秒会怎么动**。数学上表示为：

M⋅q¨+C+G=Fext*M*⋅*q*¨+*C*+*G*=*F**e**x**t*

- **M**：质量矩阵（每个部件的质量和转动惯量）
- **q̈**：加速度（每个关节/部件下一秒的角加速度和线加速度）
- **C**：科氏力和离心力（转动产生的附加力）
- **G**：重力（地球引力）
- **F_ext**：所有外力（电机驱动力、地面摩擦力、碰撞力）

Gazebo 本身不实现物理计算，而是作为框架集成 ODE、Bullet、DART 等物理引擎。碰撞检测使用 GJK 算法（凸体碰撞检测）+ SAP 算法（空间划分加速）。

**传感器仿真在做什么？**

- **激光雷达（GPU Lidar）** ：通过光线投射（Ray Casting）向场景发射数万条射线，检测与网格的交点距离。Gazebo Harmonic 已移除 Classic 版本的 `type="ray"`，统一使用 `type="gpu_lidar"`。
- **IMU**：从物理引擎读取刚体的角速度和线加速度，添加高斯噪声模拟真实传感器。
- **相机**：通过渲染引擎输出 RGB/深度图像。

### 3.2 Gazebo 与 ROS2 如何通信

Gazebo 使用自己的通信中间件 **Gazebo Transport**（基于 ZeroMQ + Protobuf），ROS2 使用 DDS——**两套系统不互通**。桥梁是 **ros_gz_bridge**。

text

```
[ROS2节点] ←→ [ros_gz_bridge] ←→ [Gazebo Transport] ←→ [Gazebo仿真引擎]
     ↓                                ↓
  DDS通信                       物理引擎+传感器+渲染
```



`ros_gz_bridge` 在 ROS2 话题和 Gazebo 话题之间建立**双向映射**。例如激光雷达数据从 Gazebo 的 `/scan` 话题翻译成 ROS2 的 `/scan` 话题。

### 3.3 仿真器选型：各有各的战场

| 维度         | Gazebo          | Isaac Sim           | Webots              | MuJoCo                  |
| :----------- | :-------------- | :------------------ | :------------------ | :---------------------- |
| **开源协议** | Apache 2.0      | 闭源（免费使用）    | Apache 2.0          | Apache 2.0              |
| **物理引擎** | ODE/Bullet/DART | PhysX 5 (GPU加速)   | ODE                 | 自研（支持MJX GPU加速） |
| **ROS2集成** | 原生官方标配    | 通过 isaac_ros 包   | 通过 webots_ros2 包 | 社区包                  |
| **渲染质量** | 中              | 极高（RTX光线追踪） | 中                  | 低（侧重物理）          |
| **典型场景** | 通用机器人仿真  | AI/视觉/数字孪生    | 教育/快速验证       | 强化学习/运动控制       |

**选型逻辑**：不知道用什么就用 **Gazebo**——它是 ROS 官方标配，社区最大，踩坑有解。**Isaac Sim** 适合需要高保真视觉或数字孪生的场景。**MuJoCo** 适合强化学习和足式机器人接触动力学研究。**Webots** 适合教育和快速原型验证。

## 四、控制与驱动：ros2_control

### 4.1 解决什么问题

同一个机器人，在仿真里跑得好好的，换到真机上还要重新写一遍控制代码吗？`ros2_control` 要解决的就是这个问题——**让同一套控制算法无缝运行在仿真和真机上**。

### 4.2 三层架构

`ros2_control` 采用分层设计：

text

```
┌─────────────────────────────────────────────────────┐
│              Controller Manager                     │
│  ┌──────────────┐  ┌──────────────┐               │
│  │ diff_drive   │  │ joint_traj   │  ...          │
│  └──────────────┘  └──────────────┘               │
└─────────────────────────────────────────────────────┘
                        ↓
               Resource Manager
                        ↓
       ┌────────────────┴────────────────┐
       ↓                                 ↓
┌─────────────────┐           ┌─────────────────┐
│ GazeboSimSystem │           │ RealHardware    │
│ (仿真插件)      │           │ (真机插件)      │
└─────────────────┘           └─────────────────┘
```



- **Controller（控制器）** ：实现具体控制算法——`diff_drive_controller`（差速控制）、`joint_trajectory_controller`（关节轨迹控制）等
- **Controller Manager**：管理控制器的加载、卸载和执行循环
- **Hardware Interface（硬件接口插件）** ：与底层硬件（仿真或真机）通信

### 4.3 仿真与真机的“无缝切换”

关键机制在**硬件接口层**：

- **仿真模式**：使用 `gz_ros2_control/GazeboSimSystem` 插件。`gz_ros2_control` 插件**自动加载 controller_manager**，然后通过 spawner 启动控制器。每个物理步（通常 1000Hz）执行：读取 Gazebo 关节状态 → 传给 Controller Manager → Controller 计算指令 → 写回 Gazebo 关节
- **真机模式**：使用自定义硬件插件（如通过串口/CAN/ETH 读写电机）

在 URDF 中通过 `<gazebo>` 标签声明控制器插件，上层所有控制器——`diff_drive_controller`、`joint_state_broadcaster`——**完全不用修改**。切换只需改一行配置。

**核心价值**：**一次建模（URDF），一套控制（ros2_control），两种部署（仿真调参 + 真机运行）** 。

## 五、感知与定位：SLAM

### 5.1 SLAM 解决什么问题

SLAM（Simultaneous Localization and Mapping）要回答两个问题同时求解：**“我在哪？”** 和 **“周围长什么样？”** 。机器人在未知环境中一边移动，一边用传感器数据估计自身位置，同时构建环境地图。

主流技术路线已从早期的**滤波法**（EKF SLAM、粒子滤波）演进到**图优化法**——当前几乎所有实用 SLAM 系统都基于图优化。

**图优化的核心思想**：

1. 机器人每走一步，记录一个**位姿节点**（pose node）
2. 两次位姿之间的相对运动（来自里程计）构成**约束边**（odometry edge）
3. 当机器人回到已访问区域，通过扫描匹配检测到**闭环**，添加闭环约束边
4. 用优化算法（如 iSAM2）调整所有位姿节点，使所有约束的总体误差最小

### 5.2 三种主流方案

**（1）slam_toolbox——ROS2 官方推荐**

`slam_toolbox` 是当前 ROS2 官方推荐的 2D SLAM 方案，基于 Karto SLAM 的图优化架构。

特点：

- **轻量**：在树莓派等资源受限平台上，CPU 负载仅约 22%
- **地图质量高**：多项对比研究表明，slam_toolbox 在地图质量和轨迹估计精度方面表现最佳
- **支持终身制图**（Lifelong Mapping）——地图构建完成后仍可持续优化和更新
- 与 Nav2 深度集成
- 适合室内移动机器人、服务机器人、仓储 AGV

**（2）Cartographer——Google 出品，适合大规模建图**

Google 开源的实时 SLAM 方案。核心思想是 **子图（Submap）+ 闭环检测**：

- 每帧激光扫描与前一帧匹配，累积成**子图**
- 新子图与历史子图用**分支定界（Branch and Bound）** 快速匹配检测闭环
- 用 Ceres Solver 做全局优化

适合**大规模室内建图**（如办公楼、仓库），但计算开销比 slam_toolbox 大——在相同硬件上，Cartographer 可能无法保证全局轨迹一致性。

**（3）RTAB-Map——3D 视觉 SLAM**

基于**外观**的实时建图（Real-Time Appearance-Based Mapping），特点是**支持 RGB-D 相机、激光雷达和立体相机，输出 3D 点云地图**。闭环检测使用**词袋模型（Bag-of-Words）** 快速检索历史关键帧。

适合需要**3D 环境感知**的场景（如视觉导航、人形机器人），常与 slam_toolbox（做 2D 建图）和 Nav2（做导航）配合使用。

### 5.3 选型建议

| 场景                          | 推荐方案         | 计算开销       | 闭环检测     | 地图类型          |
| :---------------------------- | :--------------- | :------------- | :----------- | :---------------- |
| 室内 2D 激光雷达机器人        | **slam_toolbox** | 低（~22% CPU） | 图优化闭环   | 2D 占据栅格       |
| 大规模室内建图（办公楼/仓库） | **Cartographer** | 中-高          | 子图匹配闭环 | 2D/3D 占据栅格    |
| 需要 3D 地图或视觉传感器      | **RTAB-Map**     | 高             | 词袋模型闭环 | 3D 点云 + 2D 网格 |

## 六、定位：AMCL

### 6.1 定位解决什么问题

SLAM 解决的是“第一次来这个地方，边探索边建图”。但**地图建好后，下次启动机器人时，它怎么知道自己在地图上的哪个位置？**

这就是 **Localization（定位）** 要解决的问题——**地图已经有了，我现在在哪？** 定位是导航的前置条件：不知道自己在哪，就无法规划去目标点的路径。

### 6.2 AMCL 的原理

AMCL（Adaptive Monte Carlo Localization，自适应蒙特卡洛定位）是 Nav2 生态中的标准定位方案。它基于**粒子滤波（Particle Filter）** 算法：

**核心思想**：用一群“粒子”来表示机器人可能的位置，每个粒子代表一个假设位置 + 方向。粒子越集中，说明定位越确定。

**工作流程**：

1. **初始化**：在地图上随机撒一堆粒子（机器人可能在的任何位置）
2. **预测**：机器人移动时，所有粒子跟着移动（根据里程计数据）
3. **更新**：机器人观测到传感器数据（如激光雷达扫描）后，给每个粒子打分——观测越吻合的粒子得分越高
4. **重采样**：淘汰低分粒子，在高分粒子附近复制新粒子
5. **自适应**：当定位不确定时（粒子分散），增加粒子数量；确定时减少，节省计算

**与 Nav2 的配合**：AMCL 节点持续发布 `map → odom` 的 TF 变换，将机器人的位置对齐到全局地图。Nav2 的规划器依赖这个变换才能正确规划路径。

### 6.3 定位 vs SLAM：什么时候用什么

| 场景                                         | 使用方案                                                  |
| :------------------------------------------- | :-------------------------------------------------------- |
| 第一次进入未知环境，需要建图                 | **SLAM**（slam_toolbox / Cartographer）                   |
| 地图已有，机器人重新启动                     | **AMCL**（纯定位，不修改地图）                            |
| 地图已有，但环境有小变化（如新增临时障碍物） | **AMCL + 局部代价地图更新**（全局地图不变，局部实时更新） |

## 七、规划与导航：Nav2

### 7.1 Nav2 解决什么问题

给机器人一个目标点（在地图上点一下），它怎么自己走过去？Nav2 要解决的就是这个**自主导航**问题——从目标点到控制指令的完整链路。

### 7.2 分层架构：战略 vs 战术

Nav2 将导航拆成两个层次：

**全局规划（战略层）** ——“走哪条路”

- 在静态地图上找一条从起点到终点的路径
- 可选算法：
  - **Smac Planner（混合A\*）** ：Nav2 默认，考虑车辆运动学约束（最小转弯半径）
  - **NavFn**：基于经典 A*，简单快速，不考虑运动学
  - **ThetaStar**：A* 的变体，允许路径穿越网格顶点，路径更短

**局部规划（战术层）** ——“当前这一帧怎么走”

- 实时生成速度指令跟踪全局路径，同时躲避动态障碍物
- 可选算法：DWB、MPPI、RPP（Regulated Pure Pursuit）等

**代价地图（Costmap）** ：维护障碍物信息，分全局代价地图（静态地图 + 静态障碍物）和局部代价地图（实时传感器障碍物）。

**行为树（Behavior Tree）** ：编排整个导航任务的状态机——收到目标 → 规划 → 执行 → 成功 / 失败恢复。

### 7.3 两种局部规划器对比

| 维度           | DWB                                                          | MPPI                                                      |
| :------------- | :----------------------------------------------------------- | :-------------------------------------------------------- |
| **算法思想**   | 速度空间采样 + 打分择优                                      | 随机采样 + 迭代优化的 MPC                                 |
| **核心机制**   | 在“能做到的速度范围”里采样几百种 `(v, ω)`，模拟轨迹，用代价函数选最优 | 多轨迹并行采样 + 代价评估，用模型预测路径积分优化控制指令 |
| **控制平滑度** | 一般（可能产生航向摆动）                                     | 优秀（平滑轨迹生成）                                      |
| **控制能耗**   | 中                                                           | 最低                                                      |
| **计算开销**   | 低                                                           | 高（需 GPU 加速或降参）                                   |
| **动态避障**   | 良好                                                         | 优秀                                                      |
| **窄通道表现** | 可能小幅摆动                                                 | 更优                                                      |
| **适用场景**   | 结构化环境、资源受限平台                                     | 复杂动态环境、高算力平台                                  |
| **选型建议**   | **低成本首选**                                               | **最强动态、最先进**                                      |

## 八、调试与排障

### 8.1 ros2 bag——数据录制与回放

`ros2 bag` 是 ROS2 的**数据记录仪**。可以录制所有话题数据到文件，事后离线回放——**把真机运行场景“搬”到办公桌上调试**。

**为什么需要它？**

- **问题复现**：真机上出了问题，录一段 bag，回到办公桌上离线回放调试，不用重复跑实验
- **算法对比**：同一段 bag 数据，跑不同的 SLAM 算法或规划器，对比效果
- **CI/CD**：自动化测试中，用 bag 数据作为固定输入，验证算法输出是否符合预期
- **现场数据记录**：商业机器人（如自动驾驶配送车、割草机器人、巡检机器人）通常高频记录摄像头、IMU、里程计、定位、控制指令和诊断数据

**推荐格式**：使用 **MCAP 存储格式**，比默认的 SQLite3 性能更好，支持更大的文件和更快的读写速度。ROS2 Jazzy 已将 MCAP 作为默认格式。

bash

```
# 录制（使用 MCAP 格式）
ros2 bag record -s mcap /topic1 /topic2

# 查看信息
ros2 bag info -s mcap your_recording.mcap
```



### 8.2 ros2 doctor——系统诊断

`ros2 doctor` 检查系统状态：所有节点是否正常、话题是否有订阅者、网络是否通畅。快速定位“为什么我的节点没反应”这类基础问题。

### 8.3 rqt 系列——轻量 GUI 工具

ROS2 自带的一组图形化调试工具：

- `rqt_graph`：节点拓扑图——谁在发布、谁在订阅，一目了然
- `rqt_console`：日志查看器——集中查看所有节点的输出
- `rqt_plot`：快速画曲线
- `rqt_topic`：话题监控

### 8.4 常见问题速查（来自实际工程踩坑）

| 症状                               | 根因                         | 修复                                     |
| :--------------------------------- | :--------------------------- | :--------------------------------------- |
| RViz 报 `Frame [x] does not exist` | 根 link 带惯性               | 根用无惯性的 `base_footprint`            |
| 轮子“歪”或“躺”                     | `<cylinder>` length 沿 Z 轴  | 绕 X 轴转 90°：`rpy="${pi/2} 0 0"`       |
| 车不动                             | Twist vs TwistStamped 不匹配 | Nav2 配置 `enable_stamped_cmd_vel: true` |
| `Moved backwards in time`          | `use_sim_time` 未统一        | 所有节点加 `use_sim_time: true`          |
| `/clock` 异常大                    | 残留 Gazebo 进程             | `pkill -f 'gz sim'`                      |
| 激光雷达不加载                     | Harmonic 移除 `type="ray"`   | 用 `type="gpu_lidar"`                    |
| 传感器 frame_id 带前缀             | URDF→SDF 转换挂载错误        | 加 `<gz_frame_id>` 显式指定              |
| `gz sim` 命令找不到                | vendor 包安装方式            | 直接运行 `gz sim`，不用检查 which        |

## 九、完整开发流程

text

```
① CAD 画图（Onshape / SolidWorks / Fusion 360）→ 导出 URDF
       ↓ （微调：惯性参数、关节限位、传感器、碰撞体简化）
② RViz2 可视化验证模型结构
       ↓
③ Gazebo 仿真 + ros_gz_bridge → 验证物理和传感器
       ↓
④ ros2_control 调参（PID / 速度曲线）
       ↓
⑤ slam_toolbox 建图（或 Cartographer / RTAB-Map）
       ↓
⑥ AMCL 定位（地图已有，定位自身）
       ↓
⑦ Nav2 导航调试（全局规划 Smac + 局部规划 DWB/MPPI）
       ↓
⑧ 全链路可视化（PlotJuggler / Foxglove / rqt）
       ↓
⑨ ros2 bag 录制现场数据 → 离线调试 / 算法对比 / CI 验证
       ↓
⑩ 替换硬件接口插件 → 真机部署
```



**每个环节的可替换性**：

- **CAD 建模**：Onshape（云端，原生 URDF 导出）/ SolidWorks（桌面，需插件）/ Fusion 360
- **仿真器**：Gazebo（通用）/ Isaac Sim（AI/视觉）/ Webots（教育）/ MuJoCo（强化学习）
- **SLAM**：slam_toolbox（轻量稳定）/ Cartographer（大规模）/ RTAB-Map（3D 视觉）
- **定位**：AMCL（Nav2 标配粒子滤波定位）
- **全局规划器**：Smac Planner（默认，考虑运动学）/ NavFn（简单快速）/ ThetaStar（路径更短）
- **局部规划器**：DWB（低算力，低成本首选）/ MPPI（高算力动态避障）
- **可视化**：RViz2（3D）/ PlotJuggler（信号分析）/ Foxglove（全栈）
- **调试**：ros2 bag（数据录制回放）/ ros2 doctor（系统诊断）/ rqt 系列（轻量 GUI）
